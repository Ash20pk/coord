Documentation

knoot coordinates several coding agents working one repository. Agents claim files before writing them, hold them on a short lease, and are handed the holder's identity and intent when a file is busy.

Install

One binary provides the relay, the daemon, the hook shim and the CLI. Install it on every machine that runs agents.

cargo install --git https://github.com/Ash20pk/knoot

Prebuilt static Linux binaries are attached to the nightly release on GitHub. macOS builds from source.

The hooks call knoot by name so they resolve on every machine that has it on PATH. If yours lives somewhere unusual, set KNOOT_BIN.

Enrol a repository

Run this once per repository. It writes .knoot.toml and the hook configuration, both of which are meant to be committed, so anyone who clones the repository is enrolled with no setup.

knoot init --relay wss://knoot.dev/ws

Then, once per machine, store the agent token and run the daemon.

knoot login --relay wss://knoot.dev/ws --token <token>
knoot daemon

Tokens deliberately do not live in .knoot.toml. That file is committed, and a secret must never ride along with it. Credentials go to ~/.knoot/credentials.toml at mode 0600, or the KNOOT_TOKEN environment variable for CI.

Verify it is on

knoot fails open, so from inside an agent a broken install looks exactly like a quiet one. knoot status is how a person tells the difference.

knoot statusreal output
[ok  ] binary    /usr/local/bin/knoot
[ok  ] repo      ~/project (id: repo-fade58f512a66c42)
[ok  ] hooks     6 events, resolved from PATH
[ok  ] daemon    responding
[ok  ] relay     wss://knoot.dev/ws (token: present)

coordination is on.

Anything less than that prints what is wrong and the command that fixes it.

Wire up an agent

knoot never talks to a model. It reads a JSON payload on stdin and answers on stdout, so anything that can run a command before it writes a file can be coordinated.

Claude Code

knoot init writes the hook configuration for you, into .claude/settings.json in the repository. Restart any sessions that were already open.

Any other agent

Call the shim yourself before each write and honour the answer. It is the same code path the built-in integration uses.

your agent, before writing a file
echo '{"hook_event_name":"PreToolUse",
       "session_id":"'"$SESSION"'",
       "cwd":"'"$PWD"'",
       "tool_name":"Edit",
       "tool_input":{"file_path":"src/auth.js"}}' \
  | knoot hook

A permitted write produces no decision. A refused one returns permissionDecision: "deny" and a reason string meant to be put straight into the model's context. Feed that string back to the model rather than summarising it: naming the holder and their intent is what makes an agent re-plan instead of retry.

People

Developers collide with agents too. Wrapping $EDITOR in the same call puts a person in the same log, holding leases the same way.

Messages and notifications

Blocking alone is not coordination. Being denied a path registers interest in it. When the holder releases it, by finishing, ending, or letting the lease lapse, every waiter is told, along with what the holder was doing.

Delivery rides the turn-end hook, so notice arrives the moment an agent tries to stop rather than whenever a person next types. A per-user cap means a chatty peer can never keep a session spinning.

Agents also write to each other directly.

knoot msg priya "auth.js is yours, exports are stable"
knoot msg all "goal is green, stop editing"

Identity comes from KNOOT_USER, falling back to $USER. Set it per session to give agents readable names in conflict briefs.

The hosted relay

Sign in to the console, create a team, and mint one agent token per machine. Tokens are stored as hashes, so an existing one can never be shown again, only replaced.

The console shows the live event log for every repository your team has connected, which is also the fastest way to confirm coordination is really on.

Your own relay

The relay is one command. Unauthenticated is right for 127.0.0.1 and wrong for anything else, so give it a shared secret and it requires one.

KNOOT_RELAY_TOKEN=$(openssl rand -hex 24) knoot relay --listen 0.0.0.0:7420

Use wss:// off-machine. A bearer token over plaintext is a token anyone on the path can take. Terminate TLS with a proxy in front of the relay.

A relay that refuses you still fails open. A rejected token means coordination is off, not that anyone is blocked: the daemon says so once on stderr, and every edit is allowed. An operator's mistake cannot become an outage for the team.

The deploy/ directory provisions a relay on a fresh Ubuntu host: TLS terminated by Caddy in front of a loopback-bound relay, systemd keeping it up, and a token generated on the box rather than in the repository.

Backups

The event log is the product, so it is protected in two layers that fail differently.

  • Nightly snapshots on the box. A sqlite3 .backup, never cp, which half-copies a write-ahead database into one that restores as corrupt. Gzipped, seven kept. This covers a bad delete or a corrupted page.
  • Continuous replication off the box via Litestream, which covers losing the host: ten seconds of loss rather than a day. It needs object-storage credentials, so it turns itself on only once they exist and says so loudly while it is off.

Hook protocol

Every payload is a single JSON object on stdin. The fields knoot reads:

FieldMeaning
hook_event_nameOne of SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop, SessionEnd.
session_idStable identifier for this agent session. Distinguishes two sessions run by the same person.
cwdAbsolute path inside the enrolled repository.
tool_nameEdit, Write or Bash. Others are ignored.
tool_input.file_pathThe file about to be written.
tool_input.commandFor Bash: the command line, parsed for write targets.
promptOn UserPromptSubmit: summarised into the intent sentence peers are shown.

A refusal comes back as hookSpecificOutput.permissionDecision: "deny" with a permissionDecisionReason string. SessionStart instead returns additionalContext, listing the other active sessions and what changed under you since your last turn.

SessionStartadditionalContext, real output
knoot: 2 other active session(s) on this repo right now:
- priya on branch main — "Add refreshSession() to the auth module"
  [working in: src/tokens.js]
- ash on branch main — "Refactor session handling to use short-lived tokens"
  [working in: src/auth.js]
Avoid editing files they are working in; you will be blocked with
details if you try, and told automatically when a file you were
blocked on is released.

Shell writes are gated too, or the scheme would be optional. Redirects, heredoc targets, tee, sed -i, cp, mv, rm and dd of= are parsed out and checked. Quoting is respected and heredoc bodies are skipped.

Event types

One sequenced log per repository. These are the types you will see in the console and in knoot watch.

EventMeaning
session_startedAn agent joined, with its branch.
intent_declaredThe sentence peers are shown when they are blocked.
claim_acquiredA file was taken on a lease.
claim_deniedSomeone asked for a held file and was given a brief.
file_writtenA permitted write landed.
claim_releasedThe holder let a file go.
path_freedA lease lapsed; waiters were notified.
messageAn agent wrote to a peer or to everyone.
ungated_writeA write knoot could not gate landed on someone's claim. Detection, not prevention.
session_endedAn agent left; its claims were dropped.

Known limits

  • Interpreters are detected, not blocked. python3 -c "open(...)" writes first and is recorded second.
  • Attribution under concurrent writes is inferred. The working tree is shared, so a peer's edit lands inside our audit window too. Authorship comes from their file_written event; if that has not arrived, an ungated write can be attributed to the wrong session.
  • Sessions sharing a name share a mailbox. Mail is keyed by user, so two sessions running as the same KNOOT_USER both receive its notes.
  • Fail-open is ambiguous by design. An allowed edit and an unreachable daemon look identical from the agent's side. Check knoot status.
